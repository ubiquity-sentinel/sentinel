## 1. Where the holds come from

**Discovery.** `createTakeoverDiscovery`
(`src/host/existing-pr-discovery.ts:91-307`) reads the issue's native PR
associations and also scans the issue title and body for PR URLs (`:60-88`). It
never checks who wrote a PR. Each park reason comes from a specific line:

- `foreign_repository`: a PR URL that points at another repo appears in the
  issue text (`:137`, which is why the passport holds list no PR numbers), or an
  associated PR lives in another repo (`:141`, `:199-202`).
- `ambiguous`: more than one open PR is associated (`:163`).
- `fork_head`: the PR comes from a fork (`:203-206`).
- `association_unproven`, `head_moved`, `source_changed`, `custody_unproven`,
  `candidate_divergent`, `unwritable_branch`, `queue_custody`, `protected_path`:
  `:160`, `:172`, `:180`, `:191`, `:198`, `:208`, `:213`, `:218`, `:237`,
  `:243`, `:250`, `:261`, `:265`, `:272`, `:280`.

**Writer.** `park()` in `src/repair/loop-existing-pr.ts:56-80` writes
`nextStep:"blocked"` with the blocker `existing PR hold: <reason> (<prs>)`. It
does this for any record without custody, even one with an implementation
already in flight (`ai-1281`). It is called at `:173-181`, `:199-201`
(`candidate_divergent`) and `:211-213` (`principal_unavailable`).

**Who calls the router.** `routeExistingPr` (`loop-existing-pr.ts:113-258`) runs
from:

- `reconcileExistingPrs` (`:261-289`), which visits every non-done issue record
  with `target.pr === null`, blocked ones included. It is called from
  `loop-cycle.ts:167`, `loop-intake.ts:91` and `matrix-planner.ts:337`.
- `loop-work.ts:98`, `loop-implementation.ts:80` and
  `loop-publication-state.ts:64`.

**Second blocker: PR creation is also gated.** For a record without custody,
`createTakeoverBoundaryGuard`
(`src/github/existing-pr-takeover-effect.ts:218-236`) runs discovery again on
every `create` and refuses unless it returns `none`. Port publication calls it
at `src/github/port-publication.ts:159` and `:227`. So changing only the router
would still block Sentinel's own PR.

**Other "existing PR hold" writers.** `loop-merge.ts:77-95`
(`self_merge_requires_owner`) and `loop-records.ts:108-113`
(`closed_publication`) only fire when a record has takeover custody
(`hasTakeoverCustody`, `src/github/existing-pr-takeover-provenance.ts:32-38`).

**What switches discovery on.** It runs only when `port.coordinationActivated`
is true (`loop-existing-pr.ts:133`), which equals `policy.activated`
(`src/host/existing-pr-takeover.ts:321-323`).

- The hosted App composition passes `capability.takeover`, which is `false` in
  `src/host/hosted-custody-capability.json:3-5` (`hosted-app-principal.ts:433`).
- The local composition, used whenever the App context is null, passes
  `{activated: takeoverRouting.status !== "inactive"}`
  (`src/host/actions-repair-host.ts:552-566`, routing read at `:392`). An
  `unknown` routing result (any failed source-evidence read,
  `hosted-app-takeover-routing.ts:42-51`;
  `hosted-app-principal-source.ts:270-279`) therefore turns discovery on. This
  is the only path that can produce live holds. I inferred it from the code and
  did not confirm it from hosted logs.

**`existingPr.custodyActivated` (`hosted-custody-capability.json:20-33`) does
not control discovery or parking.** It is the runtime custody floor. It feeds:

- maintenance compatibility
  (`ops/hosted-autonomy-runtime-compatibility.ts:53-60`)
- writer quiescence (`hosted-writer-quiescence.ts:165`)
- owner-install plan/run/supersession/recovery (`owner-install-plan.ts:114`,
  `owner-install-run.ts:124`, `owner-install-supersession.ts:166,737`,
  `owner-install-future-recovery.ts:109`)
- App `runtimeCapabilityAccepted` (`hosted-app-principal.ts:421-423`)

Flipping it is not needed for this fix. If set to false while
`queue.proofActivated` is also false, maintenance would return `ordinary`
immediately (`runtime-compatibility.ts:53-56`) and skip the bootstrap
`migration_only` routing (`:111-121`). That is a separate decision.

**Adoption (the takeover path).** For a record without custody, a discovery
`candidate` leads to `authorizeAdoption` and then `persistNativeIntent`
(`loop-existing-pr.ts:197-216`). That records the other person's PR as
Sentinel's, preserves its head and later drives that PR (`:230-253`). It is
dormant in production: `effectsAllowed` needs `policy.activated`,
`runtimeCapabilityAccepted` and contents-write
(`existing-pr-takeover.ts:109-112`), and the local composition defaults
`runtimeCapabilityAccepted` to false (`:98-99`). It is exactly what the
directive forbids, so disabling it is required. No live record has custody: 0 of
418 carry `pr-takeover-v1` evidence, a `pr_takeover:` intent, a native-preserve
blocker or a preflight hold.

**Sentinel's own PR handling stays as it is.**

- Records already bound to a PR skip routing (`loop-existing-pr.ts:124`,
  `:272`).
- Own-branch reuse and the author check stay in `port-publication.ts:177-213`,
  on the fixed `sentinel/repair/<id>` branch.
